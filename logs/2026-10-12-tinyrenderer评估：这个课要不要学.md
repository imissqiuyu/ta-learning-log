## 卡住的地方（**这次最有价值的部分**）

### ① TGA 文件头写成 19 字节

| | |
|---|---|
| **现象** | 图片出来了，但颜色和位置全乱：白点旁边多个红点 |
| **根因** | TGA 头的 `bitsperpixel` 是 **1 字节**，我写成了 `uint16_t`，整个头变 19 字节，后面所有像素**错位一个字节** |
| **解决** | 改成 `uint8_t` |
| **谁的问题** | 我（二进制格式字段宽度没逐个对） |

> **关键动作**：没有靠肉眼猜，而是**dump 出所有非黑像素的坐标和 RGB**，
> 一看数据就露馅了。

### ② TGA 原点标志位读反

`imagedescriptor` 的 bit5：1 = 文件第一行是图片顶部。
我写成「没置位才翻转」，正好反了，官方贴图读进来全是倒的。

**谁的问题**：我（这类「布尔含义」最容易反）

### ③ 第 2~6 节整张图上下颠倒

| | |
|---|---|
| **现象** | 图看着「像个头」，但和官方对不上 |
| **根因** | 我的帧缓冲内存约定是 y 向上，翻成图片 y 向下是**写文件时**做的。但我在映射函数里**又手动写了个负号** —— 等于翻了两遍 |
| **发现方式** | 把第 6 节（手写公式）和第 7 节（矩阵）对比：差 224576 像素；**把其中一个上下翻转后再比，只差 3 个像素** → 说明只差一个垂直翻转 |
| **为什么确定是第 6 节错** | 第 7 节走的是标准 OpenGL 矩阵约定 |
| **谁的问题** | 我 |

> 这条最值得记：**看起来「挺像个头」不代表方向对**。
> 我是靠「两个实现对比 + 猜测性变换」定位的，不是靠眼睛。

### ④ exe 一启动就闪退（0xC0000139）

编译成功，运行直接退出。

**根因**：这台机器 PATH 里 **Anaconda 的 `Library\mingw-w64\bin` 排在 `D:\mingw` 前面**，
它带了个**旧版 `libstdc++-6.dll`**。我们的 exe 用 g++ 11.2 编的，需要新符号 → 加载失败。

**解决**：`-static` 静态链接。用 `objdump -x` 验证，现在只依赖系统 DLL。

### ⑤ ⭐ PowerShell 脚本静默失效（最阴的一个）

| | |
|---|---|
| **现象** | `build.ps1` 里明明写了 `-static`，编出来还是动态链接；后来加的取编译器路径那行也「不生效」 |
| **根因** | 文件存成 **UTF-8 无 BOM**，Windows PowerShell 5.1 用 **GBK** 解码。GBK 把 `0x81~0xFE` 当双字节前导，而中文标点（`！` `。` `）`）的 UTF-8 尾字节**正好在这个区间** —— 紧跟的换行符被当成第二个字节**一起吃掉了** |
| **后果** | `$flags = @(...,"-static")` 和 `$gxx = ...` 两行**变成了上一行注释的一部分，静默消失，零报错** |
| **验证方法** | `[i for i in range(len(b)-1) if b[i]>=0x81 and b[i+1]==0x0A]` 数危险位置 |
| **解决** | 存成**带 BOM 的 UTF-8** + `build.cmd` 优先用 `pwsh`（PowerShell 7） |
| **谁的问题** | 环境（Windows 的经典老坑），但**我没第一时间怀疑编码**，绕了好几圈 |

**三条通用教训**：
1. 中文注释的脚本/bat，一律存 **UTF-8 with BOM**
2. 「改了代码但行为没变」，先怀疑**文件根本没被正确读取**，再怀疑逻辑
3. **静默失效比报错危险得多**

## 学到什么

### 技术层面

| 学到 | 说明 |
|---|---|
| **帧缓冲就是一坨内存** | 64×64 RGB = 12288 字节。渲染 = 往正确位置写字节 |
| **Bresenham 全程无除法** | 只有整数加减和比较。三个技巧：陡的对调、保证左→右、误差累加过阈值才进格 |
| **重心坐标是整门课的枢纽** | 一个工具同时解决「在不在里面 / 覆盖哪些像素 / **顶点数据怎么插进内部**」 |
| **Z-Buffer 不排序** | 每像素存深度，O(1) 比较，天然支持三角形穿插。画家算法做不到 |
| **透视是除法的副产品** | 投影矩阵**不做除法**，只是把距离写进 w；后面 ÷w 时远的东西自然被缩小 |
| **透视校正插值** | 屏幕空间线性成立的是「属性/w」。**GPU 保留 1/w 不是为了深度，是为了插值** |
| **IShader 就是 GPU 的全部抽象** | 只能写两个函数：vertex() 和 fragment()。UE5 材质节点图最后编译成的就是它们 |

### 方法论层面

| 学到 | 来源 |
|---|---|
| **看图不算验证，要看数据** | dump 像素坐标直接定位 TGA 头 bug |
| **两个实现对比 + 猜测性变换** 能快速定位「差一个翻转/符号」类 bug | 上下翻转后只差 3 像素 |
| **同一套约定只在一处做转换** | 翻了两遍导致全反 |
| **二进制格式的字段宽度必须逐个对规范** | 编译器不会拦你 |
| **「像个头」是错觉，方向对不对要靠约定推** | 坑 ③ |

## 卡住的地方

### ① 正面/背面绕序符号搞反（唯一一个真 bug）

| | |
|---|---|
| **现象** | 第 13 节的描边壳把**整个头盖成黑色**，只剩一条细线 |
| **根因** | 屏幕空间有向面积的符号约定我写反了。以为「正面 area<0」，实际**正面 area>0**。于是"只画背面"变成"只画正面"，外扩后的正面把本体整个盖住了 |
| **怎么查的** | **不靠直觉，用已知几何验算**：拿第 9 节那块地面（法线朝上、肯定朝相机），把三个顶点一路手算到屏幕坐标，得到 `area = +9959040` |
| **谁的问题** | 我 |

> **教训**：绕序、左右手坐标系、翻转符号这一类东西，
> **永远用手算一个已知案例来确认**，不要凭"我觉得"。

### ② 黑色描边在黑色背景上看不见

第 13 节一开始背景是黑的，描边也是黑的，等于白做。

**教训**：调试可视化的时候，**先想想"这个东西在当前环境里看得见吗"**。

### ③ 透视失真的对比一开始不够明显

第一版用官方 `floor.obj`（只有 2×2 单位），关掉透视校正后画面几乎没变化，

**教训**：**做对比实验要把变量推到位**。差异不明显时，先问
"是不是我这个测试用例本身就不够极端"，而不是怀疑结论。

## 学到什么

### 技术层面（这一段新增）

| 学到 | 说明 |
|---|---|
| **光照就是一个点积** | `max(0, N·L)`。朗伯余弦定律，纯几何 |
| **Gouraud vs Phong** | 逐顶点算 vs 逐像素算。插值出来的法线**必须重新归一化** |
| **透视校正是 1/w 的产物** | 屏幕空间线性成立的是「属性/w」。**GPU 保留 1/w 不是为深度，是为插值** |
| **法线贴图为什么是淡蓝紫色** | "没扰动"的法线是 (0,0,1) → RGB (0.5,0.5,1.0) |
| **为什么用切线空间** | 可复用（贴图不绑朝向）、可形变（跟骨骼走）、可压缩（z 恒正） |
| **TBN 从哪来** | 顶点位置差 ←→ UV 差，解一个 2×2 线性方程组 |
| **阴影贴图 = 两次渲染 + 一次比较** | 没有光线求交、没有阴影体 |
| **阴影痤疮和彼得潘是同一个旋钮的两端** | bias 小了长痤疮，大了影子脱开 |
| **UE5 的 VSM 全在解"锯齿"** | 原理没变，是分辨率的工程优化 |
| **SSAO 是后处理，所以必须有 G-Buffer** | 它需要每个像素的位置+法线，颜色图里没有 |
| **卡通渲染三件套** | 色阶化（一行 floor）+ 反向外扩壳描边 + 边缘光。**全都是非物理的** |

### 最值钱的一条：一个参数量级

第 12 节 SSAO 实测：800×800 × 32 采样，Release 编译 **0.5 秒**。
真 GPU 上同分辨率是**零点几毫秒**。

> **差三个数量级。**
> 这一下就把「为什么要用 GPU」「为什么 GPU 能做那么多事」讲清楚了 ——
> 不是"快一点"，是**差了 1000 倍**。
