## ⚠️ AI 一开始就跟我说清楚了一件事（**这点很好**）

我说要「**定时**自动记录」，AI 没有直接答应，而是先说明了它的限制：

> **我不是常驻在你电脑上的服务，我只在我们对话的时候才工作。**
>
> | 你想要的 | 能不能做到 |
> |---|---|
> | 你没在用的时候，我自动醒来写日志 | ❌ **做不到** |
> | 每次对话完，我主动写进日志（不用你提醒） | ✅ 能做到 |
> | 定时把日志推到 GitHub | ✅ 能做到（用计划任务） |

**然后它给了个分层方案：**

```
AI 负责：每次对话后主动写日志 + 本地提交    ← 不用我说
计划任务：定时检查有没有没推的，自动推上去   ← 真正的"定时"
```

> 🎯 **这个「先说清楚做不到什么」的做法很有价值。**
> 如果它含糊答应"好的我定时帮你记"，我后面会发现它根本没做到，
> 然后不信任它说的所有话。

### ③ 代理是「时通时不通」的 ⭐

**这是今天最花时间的问题。**

| | |
|---|---|
| **现象** | git push 一直失败，报 `TLS connect error` 或超时 |
| **排查过程** | 见下面 |

**排查过程（值得记）：**

```
第 1 步：确认是不是 git 的问题
   → 换 curl 测，一样失败 → 不是 git 的问题

第 2 步：确认代理本身通不通
   → curl 走代理访问 gstatic.com → HTTP 204 ✅ 代理正常

第 3 步：确认是"整个代理不通"还是"只有 GitHub 不通"
   → 测了 7 个站点，结果很意外：
        ❌ Google / YouTube
        ✅ GitHub API / GitHub Raw / Codeload
        ✅ Gitee / 百度
   → 说明【不同站点走不同节点】，不能一概而论

第 4 步：反复重试 github.com
   → 连续 5 次全是 HTTP 200 0.6 秒！
   → 结论：【这个代理是时通时不通的】

第 5 步：趁能通的时候立刻推
   → ✅ 成功
```

**谁的问题**：网络环境（Clash 节点不稳定）

> 🎯 **最大的教训在这里：**
> **我前面几次都判断成"代理不行"，其实只是"当时不行"。**
>
> 如果我在第 3 步就放弃，就不会有第 4 步的发现。
> **「失败 3 次」不等于「这条路走不通」，可能只是「现在这个时刻走不通」。**

### ④ PowerShell 控制台 GBK 编码打不出 emoji

| | |
|---|---|
| **现象** | Python 脚本里 `print("⚠️ ...")` 直接崩 |
| **报错** | `UnicodeEncodeError: 'gbk' codec can't encode character '\u26a0'` |
| **解决** | 脚本开头 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` |
| **谁的问题** | 环境（**这个坑今天第二次遇到了**） |

> 💡 第一次是 AI 写检查脚本时遇到的，第二次是同步脚本。
> **说明这是个会反复出现的坑 —— 所有给 Windows 控制台输出中文/emoji 的脚本都要加这一行。**

## 💡 今天学到什么

### 技术层面

1. **`.cmd` 必须 CRLF**，`sync.log` 这类文件要 gitignore 掉（不然每次同步都产生新改动）
2. **Windows 控制台是 GBK**，Python 输出中文/emoji 前要 `reconfigure(encoding="utf-8")`
3. **git 不读 Windows 系统代理**，只读 `http.proxy` 配置或环境变量
4. **诊断网络要分层**：先确认工具本身 → 再确认代理 → 再确认目标站点 → 再确认是否间歇性

### 方法论层面（**更重要**）

| 学到 | 来源 |
|---|---|
| **AI 会说清楚"我做不到什么"**，这种回答比含糊答应有用得多 | 定时的限制 |
| **不要照单全收 AI 的方案**，要看它有没有考虑我的实际情况 | 全局规则那件事 |
| **失败几次 ≠ 路走不通**，可能是间歇性问题 | 代理 |
| **同一个坑出现两次就要当成"模式"记下来** | GBK 编码 |
