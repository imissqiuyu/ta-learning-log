### ③ 代理是「时通时不通」的 ⭐

**这是今天最花时间的问题。**

| | |
|---|---|
| **现象** | git push 一直失败，报 `TLS connect error` 或超时 |
| **排查过程** | 见下面 |

**排查过程（值得记）：**

```
第 1 步：确认是不是 git 的问题
   → 换 curl 测，一样失败 → 不是 git 的问题

第 2 步：确认代理本身通不通
   → curl 走代理访问 gstatic.com → HTTP 204 ✅ 代理正常

第 3 步：确认是"整个代理不通"还是"只有 GitHub 不通"
   → 测了 7 个站点，结果很意外：
        ❌ Google / YouTube
        ✅ GitHub API / GitHub Raw / Codeload
        ✅ Gitee / 百度
   → 说明【不同站点走不同节点】，不能一概而论

第 4 步：反复重试 github.com
   → 连续 5 次全是 HTTP 200 0.6 秒！
   → 结论：【这个代理是时通时不通的】

第 5 步：趁能通的时候立刻推
   → ✅ 成功
```

**谁的问题**：网络环境（Clash 节点不稳定）

> 🎯 **最大的教训在这里：**
> **我前面几次都判断成"代理不行"，其实只是"当时不行"。**
>
> 如果我在第 3 步就放弃，就不会有第 4 步的发现。
> **「失败 3 次」不等于「这条路走不通」，可能只是「现在这个时刻走不通」。**

### ④ PowerShell 控制台 GBK 编码打不出 emoji

| | |
|---|---|
| **现象** | Python 脚本里 `print("⚠️ ...")` 直接崩 |
| **报错** | `UnicodeEncodeError: 'gbk' codec can't encode character '\u26a0'` |
| **解决** | 脚本开头 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` |
| **谁的问题** | 环境（**这个坑今天第二次遇到了**） |

> 💡 第一次是 AI 写检查脚本时遇到的，第二次是同步脚本。
> **说明这是个会反复出现的坑 —— 所有给 Windows 控制台输出中文/emoji 的脚本都要加这一行。**

## 💡 今天学到什么

### 技术层面

1. **`.cmd` 必须 CRLF**，`sync.log` 这类文件要 gitignore 掉（不然每次同步都产生新改动）
2. **Windows 控制台是 GBK**，Python 输出中文/emoji 前要 `reconfigure(encoding="utf-8")`
3. **git 不读 Windows 系统代理**，只读 `http.proxy` 配置或环境变量
4. **诊断网络要分层**：先确认工具本身 → 再确认代理 → 再确认目标站点 → 再确认是否间歇性

### 方法论层面（**更重要**）

| 学到 | 来源 |
|---|---|
| **AI 会说清楚"我做不到什么"**，这种回答比含糊答应有用得多 | 定时的限制 |
| **不要照单全收 AI 的方案**，要看它有没有考虑我的实际情况 | 全局规则那件事 |
| **失败几次 ≠ 路走不通**，可能是间歇性问题 | 代理 |
| **同一个坑出现两次就要当成"模式"记下来** | GBK 编码 |

### ⚠️ 卡住的地方

#### ① Edge 加了 `--remote-debugging-port` 但端口起不来

| | |
|---|---|
| **现象** | 重启 Edge 后 9222 端口没监听 |
| **排查** | 用独立 `user-data-dir` 试了一次 → **端口起来了** |
| **根因** | **Chromium 从 136 版开始**：用默认用户数据目录时，`--remote-debugging-port` **会被直接忽略** |
| **解决** | 给一个独立的 `--user-data-dir` |
| **谁的问题** | 环境（引擎的安全策略变了） |

**我的 Edge 是 153 版**，所以旧教程里的方法全部失效。

#### ② 2.6 GB 的配置目录太大

| | |
|---|---|
| **现象** | Profile 10 有 2632 MB，整个复制太慢太占地方 |
| **分析** | 其中 2.3 GB 是缓存（IndexedDB 768MB、Code Cache 660MB、Service Worker 550MB、Cache 330MB） |
| **解决** | 只复制登录状态 + 扩展，**丢掉纯缓存** → 273 MB |
| **效果** | 复制用时 8 秒 |

#### ③ `cdp.py status` 连不上，但其它命令能工作

| | |
|---|---|
| **现象** | `status` 一直报「连不上」，但 `open` / `text` 都正常 |
| **根因 1** | **Python 的 `requests` 会读 Windows 系统代理**，把本机 `127.0.0.1:9222` 也往 Clash 里绕 → `trust_env=False` 解决 |
| **根因 2** | **我自己把路径写错了** —— 版本接口是 `/json/version`，我写成了 `/version` |
| **谁的问题** | **AI**（两个都是） |

> 🎯 **第 2 个根因很典型：**
> 「同样的 `http()` 函数，为什么 `/json/list` 能用、`/version` 不能用？」
> —— 因为我**没去核对 CDP 的接口路径**，凭印象写了一个。

### 💡 今天学到什么

#### 技术层面

1. **浏览器代理扩展 ≠ 系统代理** —— 扩展只作用于浏览器自己，其它程序（git、curl）都用不上
2. **Chromium 136+ 禁用了默认目录下的远程调试** —— 必须用独立 `user-data-dir`
3. **Python `requests` 会读 Windows 系统代理** —— 连本机端口要 `trust_env=False`
4. **Chrome/Edge 配置目录里 90% 是缓存** —— 迁移时丢掉就好
5. **MV3 扩展的 service worker 会休眠** —— CDP 里看不到不代表没加载

#### 方法论层面（**更重要**）

| 学到 | 来源 |
|---|---|
| **「同样的代码，一个接口能用另一个不能」→ 先核对接口路径** | `/version` vs `/json/version` |
| **报错说"连不上"，要先分清是"网络不通"还是"请求发错了"** | `status` 的双重根因 |
| **换一种方式验证假设**（用独立目录试一次）比反复猜有效 | 定位 Chromium 限制 |
