## 学到什么

### 技术层

1. **`Transform(World→View)` 是 Matcap 的核心**
   - 用世界空间法线 → 高光"画死"在物体上
   - 用视角空间法线 → 高光跟着相机滑动 → 看起来像反射

2. **`ConstantBiasScale(Bias=1, Scale=0.5)` 一个节点顶两个**
   - `(N.xy + 1) × 0.5` = 把 -1..1 映射成 0..1

3. **UE 5.7 没有 `PreSkinnedLocalPosition`，但有 `PreSkinnedPosition`**
   - 减掉 `ObjectPositionWS` 就是"蒙皮前的局部位置"
   - **这就是探测脚本存在的意义** —— 不同版本节点不一样，不能凭记忆写教程

4. **`LocalPosition` 是蒙皮【后】的**
   - 骨骼一动，位置就变 → 用它做上下渐变，角色弯腰时渐变会滑动
   - 而且**静止姿势下完全看不出来**，只有真的播动作才暴露

### 方法论层

**① "看起来对"和"对"是两件事**

上下渐变在静止站姿下看着完全正常 —— 但播一个动作就露馅。
**验证一个做法对不对，要用它"最容易被搞坏"的场景去测。**

**② 同一个材质里留两版实现，用参数切换**

`UseSkinnedPos = 0/1`。比"改一遍→截图→改回来"强得多：
- 不会忘记改回来
- 两张图的其它条件完全一致（同一帧、同一机位）
- **而且"我把两种实现都留着做对比"本身就是个加分点**

**③ 给新手写操作步骤：位置 > 内容**

"右键搜 LocalPosition" 对熟练的人够了；对新手必须写清
"打开哪个文件 → 在哪个窗口 → 在哪块区域右键"。

**④ 探测 > 记忆**

`check_npr_nodes.py` 问引擎"你有没有这个节点"，
比 AI 拍脑袋说"应该有"可靠一万倍。

## 第 2 次对话（同一天下午）· 第 3 层 边缘光

上午做完第 1、2 层，下午接着把**第 3 层（边缘光）**两套方案都跑通了。

### 做了什么

**A · 菲涅尔边缘光**（材质内，5 个节点）
```
Fresnel(Exponent=4) → × RimColor → × RimStrength → 加进最终颜色
```

**B · 深度 Sobel 描边**（后处理材质，脚本生成 `build_npr_outline.py`）
> ScreenPosition → 4 方向 UV 偏移 → 4 次 SceneDepth 采样
>   → Custom 节点算拉普拉斯 → smoothstep → 与场景色插值
> + 一个 Unbound 的 NPR_Outline 体积挂上去

### 一天里踩的四个坑（**三个是 AI 的错**）

#### ① `post_process_materials` 这个属性不存在

> Exception: Failed to find property 'post_process_materials' on 'PostProcessSettings'

**AI 按 UI 上的标签名（"Post Process Materials"）写代码**，
但真实属性是 `weighted_blendables`（里面再套一个 `array`）。

> **UI 标签 ≠ 代码属性名。** 这种错只能靠引擎报错暴露。

#### ② float4 和 float3 不能插值

```
(Node LinearInterpolate) Arithmetic between types float4 and float3 are undefined
```

`SceneTexture` 永远输出 **float4（RGBA）**，颜色参数是 **float3（RGB）**。
中间必须加一个 `ComponentMask` 只取 RGB。

> **HLSL 是强类型的。** 任何"场景贴图 × 颜色"的地方都要先 Mask。

#### ③ 地平线出现一条 40 像素粗的红带（**这个最有价值**）

现象：角色轮廓的描边对了，但**地平线附近糊成一大片红色**。

根因：
> 深度在屏幕上是【双曲线】分布（1/z）
> → 对深度直接做二阶导，在地平线附近（z→∞）会爆炸
> → 假边缘

修法：
> 改用【逆深度 1/z】做拉普拉斯
> → 平面上 1/z 是【线性】的，二阶导 ≈ 0
> → 平地干净
> → 再按中心值归一化，远近用同一个 Scale

**改完那条红带消失了。**

> 这条值得单独记：**"为什么深度边缘光要用 1/z 而不是深度"**
> —— 面试问到这个，答得出上面这段，就是另一个层级。

#### ④ "调试参数给太温柔"（**第三次了**）

一天里出现三次：

| 哪一层 | AI 给的"好看"值 | 结果 | 改成极端值后 |
|---|---|---|---|
| 上下渐变 | 两个灰调 | 看不出 | 纯蓝/纯红 → 立刻看见 |
| 深度描边 | `EdgeScale 0.06` | 什么都没有 | `0.5` → 立刻看见 |
| 边缘光 | 亮青色 `(0.6,0.85,1.0)` | 白角色上看不见 | 纯红 + 强度 5 → 立刻看见 |

**规律：**
> **调试用的参数，必须调到"不可能看错"的程度。
> 看得见了，再往回收成好看的。**
>
> 反过来做（先给好看的）→ 你看不出"没生效"和"太淡"的区别。

**这条已经写进 `Docs/98`。**

### 我提的问题

**「为什么只有胸部和手的部分颜色发生了变化，其他地方还是白色」**

这个问题直接指向了材质的**真正缺口**：

> BaseColor 是个【纯色常数】→ 凡是被判为亮面的地方颜色一模一样
> PartRow = 0.0625（硬台阶）→ 没有过渡
> → 所以整个角色是一块白，只有 Matcap（视角相关）会局部亮

**根因：材质没有 albedo 贴图。**

> **真实角色的"颜色差异"来自贴图，不是来自光照。**
> 皮肤、衣服、腰带之所以不一样，是因为贴图不一样。

这是第 4 天出图之前必须补的一步 ——
好在 Manny 自带的 `MI_Manny_01/02` 里就有贴图可以拿来用。

#### ③ 水面特写：拍了四次才对

```python

```

**从此不再猜参数名。**

#### ⑤ 计算噪声尺度的方法（这条最实用）

```
水面的噪声用的是 LocalPosition —— 局部坐标，范围只有 ±50
（跟 actor 缩放无关，这是之前踩过的坑）

一个波的宽度 = 8000 / (2 × NoiseScale × 50)
  NoiseScale = 0.35 → 波宽 230 cm → 近景就是几个大糊块
  NoiseScale = 2.5  → 波宽 32 cm  → 适合近景
  NoiseScale = 0.06 → 波宽 1300 cm → 适合远景
```

**这是"把参数代进公式算一遍"的第二次应用**（第一次是 FogDensity）。

### 第 6 天 · 性能实测

| 材质 | 指令数 |
|---|---|
| Water | 207 |

**stat gpu（独立进程游戏，1280×720，渲染分辨率 100%）**：

> Postprocessing           1.85
> TemporalSuperResolution  1.69
> RenderDeferredLighting   1.53
> VolumetricFog            0.78
> LumenReflections         0.57
> Lights                   0.48
> ShadowDepths             0.40
> Basepass                 0.09   ← 四个材质的着色开销总和

### 今天最重要的一个结论（**推翻了前一天的**）

前一天我说："着色器复杂度显示两个发光材质最红，所以它们最贵，
优化方向是减少叠加层数。"

**实测把这个结论推翻了：**

> Basepass 0.09 ms ÷ 总 5.94 ms = 1.5%
> → 四个材质加起来只占 1.5%，绝对值上可以忽略
> → 真正吃掉时间的是【后处理 + TSR + 延迟光照 + 体积雾】这些渲染器的固定开销

**根因是搞错了"相对"和"绝对"：**

> 着色器复杂度  →  相对分布（哪片像素比别处贵）
> stat gpu      →  绝对值（这件事值不值得优化）
>
> 只看前者，会去优化一个只占 1.5% 的东西。

### 还有一个「决定不做」

本来要做「已遮罩 vs 不透明」的 Early-Z 对比（`Docs/00` 里的经典结论）。

**但 Basepass 只有 0.09 ms，两者的差值会完全淹没在测量噪声里。**

硬测只会得到一个"看起来很精确、实际无意义"的数字。
**所以决定不测，并把"为什么不做"记下来。**

> 这条和"测不出来也要给个数"正好相反 ——
> **知道什么时候不该测，和知道怎么测一样重要。**

### 学到什么

**技术层**
1. 水面噪声的"尺度匹配"：`波宽 = 场景尺寸 / (2 × NoiseScale × 局部范围)`
2. 水的"水感"来自掠射角反射，俯视时没有 → **机位比参数重要**
3. `HighResShot` 不含 HUD（`stat` 文字要系统截图）
4. `HighResShot` 不锁分辨率 → 用系统截图才能拿到 100% 分辨率的性能图
5. 性能必须在**独立进程游戏**里测，编辑器视口有 30~50% 额外开销

**方法论层**
1. **自动生成的文件名要马上收走**（会被覆盖）
2. **参数名/值要读出来，不要猜**（`list_mi_params.py`）
3. **"相对 vs 绝对"是性能分析最容易搞错的地方**
4. **测不出就承认测不出**，别编数字
5. 机位写成脚本 → 可复现、不歪、省时间

### 卡住的地方（这一天全在排查一件事）

**描边"在但不可见"，排查三轮：**

> 第 1 轮：Blendable 权重是 0
>          ← AI 第 4 天拍菲涅尔时关掉的，忘了设回来
> 第 2 轮：修权重的脚本崩在 settings.enabled
>          ← 这个属性在【体积】上，不在 settings 上
> 第 3 轮：设置了权重，回读还是 0
>          ← 【结构体数组的副本】问题

**第三个是这天最有价值的发现：**

```python
arr = settings.get_editor_property("array")   # 这是副本
arr[0].set_editor_property("weight", 1.0)     # 改的是副本里的副本
settings.set_editor_property("array", arr)    # 写回的还是旧值
```

**`get_editor_property` 拿到的是结构体数组的副本，改元素不会写回资产。
必须新建结构体对象、重建整个数组。而且它不报错 —— 只有回读才能发现。**

### 学到什么

**技术层**
1. `get_editor_property` 拿到的结构体数组是**副本**，改元素不写回（且不报错）
2. `APostProcessVolume` 的 `enabled` / `blend_weight` 在**体积**上，不在 `FPostProcessSettings` 里
3. `HighResShot` 不含 HUD（`stat` 文字要系统截图），也不含编辑器叠加层（gizmo、选中框）
4. Netlify Drop 拖文件夹就能部署，不用注册

**方法论层**
1. **"改了没生效"是这一整天的主题** —— 出现至少 8 次，
   每一次的根因都不同：实例覆盖、值没保存、关卡开错、名字对不上、
   结构体副本、体积属性位置、权重被关掉忘了开、选错了截图文件
2. **给"临时改动"建复位机制** —— 为拍一张图而关掉的开关，
   必须在拍完后复位，或者干脆脚本化
3. **让人改的东西要改不坏**（txt 比 py 安全）
